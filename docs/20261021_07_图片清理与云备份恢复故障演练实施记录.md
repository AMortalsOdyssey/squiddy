# 图片清理与云备份恢复故障演练实施记录

## TL;DR

- 0.4.1补上文件上传前的持久预约，避免进程在上传后、登记前退出时遗留无人管理的图片；注销清理保留预约等待时间，文件队列完成后才结束。
- 真实开发云已取得25个集合、51条文档与4张图片的私有备份；恢复到独立隔离集合与独立图片目录，51条记录和4张图片均回读一致。
- 真实云演练覆盖分段恢复后续传、删除一条副本后补回、目标记录变化时拒绝覆盖、历史快照引用图片的保留；媒体、删除队列和测试文件已全部清空。
- 微信提醒、多人真机、提审和正式发布继续暂缓；开发工具保留打开。没有开通付费备份或新的云环境，没有覆盖原有厨房与饭局。

## 部署坐标与范围

沿用既有免费开发云与四个函数：api、publicRead、platformCallback、maintenance。服务端为Nodejs20.19、3秒时限，维护仍由平台每5分钟触发。AppID、环境ID、身份、云文件ID、邀请信息和完整备份只留在本机忽略配置、私有文件和既有云平台。

恢复目标以`squiddy_drill_`命名，与业务集合分开；每行保存表名、原主键与完整文档。恢复文件使用独立`squiddy-restore/`目录，并把恢复文档中的所有云文件引用改为副本地址。它是隔离逻辑恢复，未执行在线切换、覆盖原业务集合或平台时间点回档。

## 图片清理的修复

| 文件与判定 | 以前 | 现在 |
|---|---|---|
| cloud/shared/runtime.js，上传前 | 上传成功后才登记文件ID，进程提前退出可能丢失清理线索 | 通过官方SDK取得真实文件ID，事务写入媒体与上传预约后才上传；普通完成后移除预约，中断后由定时任务恢复 |
| domain/maintenance.js，注销碰上上传 | 清理任务可能提前把文件预约改成普通删除 | 保留上传预约及最早回收时间，注销任务等待文件队列结束；上传完成后发现媒体已删除则立即转普通文件回收 |
| cloud/shared/runtime.js，删除返回 | 空列表可能被当成功；SDK的文件不存在错误使任务永久保留 | 只接受一条明确回执；0与SDK定义的-503003视为文件已清除，其他异常保留队列、失败次数、时间与脱敏错误码 |
| 删除结果落库 | 可能移除已被操作员纠正的同名任务 | 事务再次核对文件ID，回执属于旧文件时不清除新任务 |

维护任务按剩余时间为图片事务与删除调用留出余量；本轮发现临近时限启动长事务会让同一批任务反复中断。余量不足且尚未处理记录时，保存当前表为下一轮起点并退出；处理过部分记录后轮转，避免其他表饥饿。非法文件标识在请求平台前拒绝，并保留失败记录。故障记录只含表名、脱敏错误码和散列键。自动测试核对下一轮确实处理被推迟的图片。

新增上传预约后另用真实小程序SDK上传自绘图片，云端回读为approved，带文件ID与审核trace，确认正常上传审核主链仍可用。

没有把未审核图片变成可用图片，没有放宽客户端调用来源、图片读取鉴权、文件规则或域名检查。

## 真实云故障演练

| 场景 | 注入与独立回读 | 结果 |
|---|---|---|
| 上传后缺少媒体记录 | 在限定目录放入真实文件与到期上传预约，不建立媒体引用 | 定时任务已实际删除孤儿文件并移除预约 |
| 历史菜单仍引用图片 | 新建不挂到用户列表的隔离厨房、历史饭局及步骤图片；图片已到期 | 图片保留；移除隔离历史引用后转入回收 |
| 媒体与文件两阶段删除 | 到期且无引用媒体 | 平台先删除媒体并入队列，再删除文件；最终媒体0、队列0、测试图片0 |
| 删除成功但确认丢失 | 两条队列指向同一隔离文件，第一条实际删除，第二条收到-503003 | 暴露旧代码不收敛；已修复；平台定时任务再次处理后，第二条队列已消失 |
| 删除失败后恢复 | 非法文件标识在真实队列中失败2次并保留错误码；按旧值护栏纠正到真实测试文件 | 后续平台定时任务删除文件并移除队列 |
| 分段恢复被中断 | 先只写25条，回读后以完整计划继续 | 仅补26条；全部51条与恢复计划逐字段一致 |
| 恢复记录丢失 | 删除隔离厨房副本的一条记录，确认云端缺失后重新应用原计划 | 仅补1条；再次完整回读一致 |
| 恢复目标发生变化 | 对一条副本增加标记，再运行恢复 | 恢复拒绝覆盖；云端标记仍在，操作员移除标记后完整核对通过 |
| 备份损坏 | 对真实备份包副本修改一个字节，保持原校验值 | 在发起云写入前拒绝，原包不变 |
| 文件恢复 | 四张副本实际上传后重新下载 | 每张SHA-256均与原始文件一致 |
| 直接读取恢复数据 | 使用真实小程序SDK直接列举及按已知副本主键读取 | 列举不返回副本，指定文档读取被拒绝；管理员只读回读51条 |

中断场景采用真实云文件、数据库与中断后持久状态注入，不声称对平台云函数进程执行了强杀。原生3秒超时后的任务回读另见06号记录。演练中临时用每分钟及每10秒触发观察多轮，收尾恢复原五分钟配置并从平台回读。消费者另对云端恢复记录做离线业务回放，核对原用户仍拥有原厨房、可读取原饭局；这不代替真实云函数切换或多人真机验收。

原厨房、菜谱、用户、成员、选择与价格逐字段未变化。原饭局只有status从open变locked、revision从2变3，符合已过cutoff_at的既有读取截止逻辑，其他字段与菜单内容未变化；不将这一结果表述为全库字节未变。

## 操作工具与回滚边界

`scripts/backup.cjs`保留v1离线格式，新增v2数据库与附件整体校验。缺文件、附件损坏、非法文档与重复文件清单都拒绝恢复。所有新文件以0600创建，已有文件不覆盖。

`scripts/cloud-backup.cjs`只使用官方开发工具CLI和本机已确认的云配置，不保存云密钥。采集先后读两遍数据库与集合清单，内容变化就停止。两遍一致只能证明观察窗口稳定，不能承诺平台级原子时间点快照；需要该承诺时另评估平台能力。

```sh
node scripts/cloud-backup.cjs capture artifacts/NEW-private-backup
node scripts/cloud-backup.cjs verify artifacts/NEW-private-backup/archive-private.json
node scripts/cloud-backup.cjs plan ARCHIVE PRIVATE-file-map.json NEW-private-plan.json
node scripts/cloud-backup.cjs apply PLAN squiddy_restore_YYYYMMDD NEW-private-state.json
```

恢复前，操作员将校验过的附件上传到独立目录并准备旧文件ID到新文件ID的映射；plan拒绝使用源图片地址。apply仅允许隔离集合名，只插入缺失记录；目标出现意外数据或同主键内容不一致就停止。待确认任务写入私有状态，继续时先查旧任务与实际目标，不盲目重放。

恢复计划、回执、原始图片、云身份及源数据不得提交仓库。公开记录只保留数量、判定、代码定位与结果。演练结束后清理隔离集合、独立文件目录和临时业务记录；本机私有备份与回执保留，供回查。
