## 配额的含义与尚未得到的账号事实

文字审核接口检查用户提交的文字。每天的调用配额用于约束接口资源消耗和滥用，这是配额机制的一般作用；当前账号获配数值及其分配理由尚未取得权威回读，不能归因为个人主体、未认证、开发版或免费套餐。

本次证据来自开发云的openapi.security.msgSecCheck及其daily诊断，见[10号记录](20261022_10_内容审核日额度诊断与满额发布验证断点实施记录.md)。它证明本次拒绝与日额度有关，不能提供完整用量，也不能证明配额究竟按AppID、微信用户还是云调用通道计数。公众平台和官方文档的浏览器访问被站点安全策略直接拒绝，未改走其他入口绕过；用户手动也未找到额度页面。

因此不能把88次当作日上限，不能推算可承载用户数，也不能把等待至第二天视为底层问题已解决。审核是微信开放接口，购买CloudBase数据库或存储套餐不等于该审核配额会增加，本轮没有购买或调整套餐。

## 本次触发原因与防线缺口

| 层次 | 已确认机制或证据 | 处理 |
|---|---|---|

| 测试消耗 | 同一现有开发环境中建厨房、80道菜和前7场真实发布；至少88次成功需审核写入 | 明天只造验收所需最少数据，预先计算调用预算 |
| 无用消耗 | 旧service.execute先审核，再鉴权、查成功回执和验容量；成功请求重放、越权请求和已满额请求都可能额外调用 | 将可判定的拒绝和回执复用前移，外部审核保留在写事务之外 |
| 重试安全 | 回包丢失会保留请求号，但后续45009曾将其清除；原操作若已成功，下次可能变成新请求 | CONTENT_RATE_LIMITED保留原请求号，恢复后先走原回执；仍无自动重试 |
| 用量管理缺口 | 缺少平台权威额度回读、完整成功调用计数、全局预算与逐用户防刷指标 | 作为正式试用前未关闭风险，不能因明天40场通过就销项 |

当前能够追溯88次成功需审核写入及额外调用的代码原因，但没有平台完整计数，尚不能断言是哪一条调用恰好耗尽最后一次额度，也不能排除同一上游计数范围内的其他调用。

## 对产品和用户的实际影响

| 操作 | 文字审核日额度耗尽时的行为 |
|---|---|
| 建厨房、改厨房介绍、修改昵称、手工保存菜谱、编辑分类、发布新饭局、恢复厨房/菜谱 | 含文字的新请求会失败；不写部分业务数据 |
| 点菜提交 | 没有备注等新文字的数量/人数提交不调用该文字审核；含备注则受影响，即使只是保留备注后再次提交数量 |
| 购物清单名称或备注、饭后评价文字、反馈、确认/撤销/制作原因 | 含文字的相应写入受影响，不能笼统说只有发布受影响 |
| 读取已有菜单、饭局和历史，导出备份 | 不依赖该文字审核接口；不因这个45009自动失效 |
| 取消饭局、关闭厨房及后台数据回收 | 不依赖该文字审核；仍受各自权限和状态规则约束 |
| 图片审核与微信提醒 | 使用不同接口，不能从msgSecCheck的45009推断也已耗尽；本轮没有扩展其额度验证，微信提醒继续暂缓 |
| 成功回执重放 | 0.5.2在再次鉴权后直接复用原结果，不必重新消耗审核；内容改动返回幂等冲突 |

文字长度在服务端汇总后最多6000字符；非空文本按2000字符步长、2200字符窗口检查，因此一次业务写入可能需要1至3次审核，空文字为0次。菜谱恢复逐条保存，不是整个备份只审核一次。30名成员每人带备注提交3次就是90次短文本审核的计划示例，不代表真实发生90次，也不是账号日上限。

额度不足时，当前客户端没有后台排队自动发布。草稿和原请求号保留，恢复后由明确的重试或本次已授权验收继续，不显示假成功；超过24小时的未确认意图仍要求先核对结果，避免盲目新建。

## 0.5.2代码修复与防护边界

| 文件与函数 | 最终行为 |
|---|---|
| domain/service.js: execute / authorizeReplay | 复用同一套账号状态、资源权限与成功回执检查；审核前和写事务内均执行。普通成员不能通过附带meal_id绕过发布所需厨房角色检查 |
| domain/service.js: moderationPreflight | 对发布、菜谱保存、分类与厨房修改先确认资源权限；达到40活跃饭局、80道菜、5个厨房时提前拒绝。满额活跃索引仍核实真实饭局状态，取消后的名额可用。写事务继续保留原容量校验 |
| cloud/shared/runtime.js: moderate | daily错误明确提示“文字审核日额度已用尽，请在额度恢复后重试”，不编造恢复倒计时，仍关闭式拒绝、不自动重试 |
| src/services/api.ts: mutate | CONTENT_RATE_LIMITED保留已有请求号；网络丢回包后遇到日额度，再恢复时仍提交相同意图，不因错误类型切换而生成新饭局 |

没有使用跨用户审核缓存，没有跳过新文字审核，没有添加客户端管理接口或改变数据库规则。并发的相同新请求可能都在首次提交前通过预检查而各消耗一次审核，最终写入仍由回执去重；本轮没有宣称完全合并所有并发审核。其他字段/状态的业务校验仍可能在审核后拒绝，本轮只消除已经列明的无用调用。

额外的审核前只读事务会增加合法新写入的读取成本，仍沿用3秒函数时限。满额索引不足40时不提前加载全部饭局；明天真实40场流程必须记录耗时和超时后的回执核对，不以本地检查保证云端时延。

离线回收完成后仍有89条回执和89条审计，其中85条分别属于技术操作。原因是厨房回收按kitchen_id/meal_id/资源主键匹配，而这些回执仅有actor、action、fingerprint、result，审计使用resource字段；现有厨房回收不按这些字段删除。正常保留期为30天，不能把清理任务completed解释成这些技术元数据也已删除。

明天优先使用现有可信管理员工具，按私有的本轮资源ID、精确请求哈希、归属和数量保护性回收技术数据及对应回执/审计。先结束技术饭局；只在资源与关联行逐项验证删除后处理对应技术清理任务。原用户厨房索引仅按已回读旧值去除技术厨房，不按现用主人actor整批删除回执或审计，也不删除主人。管理员精准回收只作为测试数据清理，不冒充产品自动注销或自然回收吞吐验收。入口不可用时记录残留和任务进度，由同一自动化继续跟踪，最终删除确认前保持“清理中”。
